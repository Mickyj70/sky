# Sky v0.3.0-rc.1

Source candidate for M2 local observation history, prepared after the M2 implementation. Publish the immutable tag only after clean-source validation and green CI. This is a candidate for feedback, not a stable release or prebuilt platform distribution.

## Included

- All M1 lookups, saved watchlists and bounded foreground polling.
- Opt-in `watch run --record`, independent `history.db`, cross-run snapshot deduplication and transactional retention (default 720h).
- Offline `history` queries with registration/hex filters, UTC encounter-time bounds, deterministic pages and corrupt-data validation.
- `history export --format json|csv` with original known aircraft fields/units, missing values, provider attribution and page metadata; formula-like source text is apostrophe-prefixed in CSV.
- `history prune --before ...` previews; `--apply` deletes transactionally.
- Independent verified history/watchlist backups and non-overwriting restores.
- Repeatable native cross-version history/recovery validation in CI, preserving exact source and validation fixture identity.

## Install and try

Once the source tag is published, Go 1.24+ can install it:

```sh
go install github.com/Mickyj70/sky/cmd/sky@v0.3.0-rc.1
sky --version
sky watch add --registration G-ZBKE
sky watch run --interval 5m --max-requests 10 --record
sky history --registration G-ZBKE --since 24h --json
sky history export --registration G-ZBKE --format csv --limit 100 > history-page.csv
```

Expected version: `sky version 0.3.0-rc.1`. Normal builds need no CGO toolchain. The foreground watch stops when its process exits and uses a finite per-run request budget. It collects only observations returned during that run; it cannot retrieve earlier flights.

## Validation and recovery

Reproduce with `python3 scripts/validate_release.py --candidate-ref HEAD --report /tmp/sky-validation.json` from matching committed source. The report records all three revisions, toolchain/native platform, validator/fixture hashes, completed checks and timestamps. The full race suite covers quota/cooldown, interruption and offline provider fixtures. Native binary checks compare stored records, pagination, CSV/JSON, prune boundaries, two-way snapshots, post-prune restore, unsupported schemas and recovery refusal.

History baseline: PR #23 merge `97d6db1776c3ebbd3712dff770ebfaf23e40a5f2`. Watchlist baseline: `checkpoint/watchlists-review-2026-11-17` (`8ad2424`). Both are unreleased checkpoints, not stable releases. Synthetic history is generated by separate temporary writers compiled against each revision's real storage API; no public provider calls or production endpoint overrides are used.

Watchlist and history remain independent schema 1. This candidate introduces no migration. Back up both databases separately before changing binaries or applying pruning. M1 binaries ignore history but still use unchanged watchlists; the earlier recording baseline can read/write and restore this history schema. Restoring one database leaves the other alone. See [history](../HISTORY.md), [validation](../RELEASE_VALIDATION.md) and [recovery](../RECOVERY.md).

## Limits

- Native runtime evidence applies only to recorded runners, currently Linux. Cross-builds do not certify macOS/Windows runtime behavior. No binary/checksum assets are promised here.
- Provider receiver coverage and freshness vary. Missing observations do not establish landed or scheduled flight status.
- Only successful watch responses are recorded. Provider errors are live events; targets load once per watch run.
- The same target/source/snapshot/content retains its first local encounter/state; different snapshot times remain separate. Registration/hex aliases remain distinct.
- Retention runs on successful recording only and reuses pages without shrinking the file or imposing a hard byte cap. Explicit pruning can be recovered only from a compatible earlier snapshot.
- Query/export returns one bounded page (default 100, maximum 1000 snapshots; 16 MiB payload cap). Stop recording/pruning and freeze absolute bounds for consistent multi-page offset exports. Watch continuation metadata.
- Collected adsb.lol data remains ODbL 1.0, separately from MIT code. Exports retain attribution; review applicable provider terms before redistribution.
- No daemon, notifications, commercial flight schedules, complete airline fleets or hosted backend.

Stable `v0.3.0` needs candidate feedback and a separate final release decision. Fixes use new immutable candidates; never move this tag. M3 begins with a provider coverage/cost/storage-rights decision before integration.
